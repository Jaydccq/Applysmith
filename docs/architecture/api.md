# Local API routes

`internal/api` serves one workspace on loopback. The route table (`Routes()`:
the lists in `routes.go` and those declared beside their handlers in
`agent_tasks.go`, `approvals.go`, `cli_install.go`, `computeruse.go`,
`goals.go`, `prompts.go`, `remote_routes.go` and `schedule_proposals.go`) is
the only way a handler is registered; `applysmith routes` prints it. This file records the choices of the Phase 2 routes that the
`local-api`, `application-tracker`, `job-discovery`, `job-evaluation`,
`llm-routing` and `dashboard-ui` specs leave open.

## Wiring

`launch.Start` opens the store and hands it to `Server.Ready`, which builds the
capabilities once (`domain.go`): the model router over the vault, the tracker,
the discovery repository, the evaluator and its worker pool (started, so
interrupted jobs are settled), and closes scan records a dead process left
running. `applysmith serve` and the desktop app both start through `launch.Start`.
`Server.Shutdown` stops the listeners, then interrupts running jobs and scans,
which record their end, and only then closes the database.
`Config.Domain` (`DomainOptions`) points the model providers, the posting reader
and the discovery endpoints at test doubles; the zero value is the product.

## Package layout

An edit recompiles every package that imports the edited one, and
`internal/api` was 20.5 MB of every such recompile in the api, apply and
answer-bank areas (measurements in [development.md](../development.md),
"Build cache"). The handlers therefore moved out of `internal/api` one domain at
a time:

- `internal/api/apikit` holds the handler contract and request helpers (Call,
  Reply, Handler, Principal, Error and its constructors, query and path
  parameters, body decoding). api refers to them qualified, without aliases.
- `internal/api/<domain>api` holds one domain's handlers and the state only
  they use. A `Deps` struct carries exactly what they need from the server,
  as functions and values, never the server itself, so the package imports
  only that domain's services and an edit elsewhere does not recompile it.
  Code that builds the domain's services or wires them into api's domain
  container (the stack's construction, its health component, timers and
  delivery channels) stays in `internal/api`. A background pass is an
  `apikit.Pass` handed to the server's `startPass`.
- The route table stays in `internal/api` (`routes.go` and the route lists
  beside their handlers there), and api's handler map takes each
  domain's handlers from its `Handlers` value. The tests stay in
  `internal/api` and reach the handlers through HTTP: the layer guard holds
  test imports to the layer order, so a test that starts the whole server
  cannot sit below api.
- Order: gmail first, which fixed the pattern. Moved: gmail, knowledge,
  tracker, documents, agent's Memory and settings routes (`agentapi`),
  models, provider, schedules, signals, the answer bank's learning routes
  (`learningapi`) and the apply views (`applyapi`: a run's and a list's
  record, the questions waiting runs left and the answers that move them on,
  the Apply Next lanes and the skip list). Staying in `internal/api` as
  server wiring: remote, telegram, notify (it builds the notification stack,
  and its routes are thin calls into the stack's board, notices, settings,
  policy and Telegram gateway, synced with the server's run streams), the
  start of a signals tick (it claims the scan runner and publishes to the run
  streams), browser (thin calls into the managed browser, the sign-in sync
  state an apply run shares, and the server's event streams), the rest of
  agent (the tools' services, the pi bridge, delegated tasks, and the
  harness, whose service imports the agent runtime) and the apply chain (the
  runner and its board, the start queue and the start routes, which take the
  apply window or queue behind it, Done and Submit this form, the kept tabs,
  cancel, and the page inputs, mirrors and sign-in sessions a run reads).
  Every domain is placed.
- Measured afterwards (development.md, "Build cache"), the moves saved 2 to
  8 percent of a rebuild: `internal/api` imports every handler package and
  keeps the wiring, so an edit in any of them still recompiles `internal/api`
  and its importers. Splitting the tests by domain or splitting
  `internal/apply` would meet the same importers and is not planned, and
  `internal/answerbank/match` stays whole for the same reason.

`remote: allowed`; `internal/api/testdata/remote-routes.golden` lists them and a
test fails when the file and the table differ (see

## Rate limits

`limits.go` counts each class over a sliding minute: `general` 240 per
principal, `evaluation` 120, `input` 3,000, `pairing` 5 per source address,
the health route 600. The static catch-all `GET /{path...}` (the embedded
dashboard, its SPA fallback and the remote pairing page) is in a class of its
own, `asset`: 3,000 per source address. A cold load fetches every page's
chunks at once (75 files and the index, plus 6 to 29 API calls), so in the
`general` class the third cold load within a minute came back 429 on its
chunks and drew a blank page. The files are cheap (memory reads, gzip made
once), hashed ones are cached for a year (`immutable`) and the index is
`no-cache`, so the bucket only has to stop a flood through the remote tunnel,
where the static route is public: about forty cold loads a minute per source.
The table check refuses the class on any route that is not a public file
route. A read by the dashboard session counts against a bucket of 1,200 of
its own (see Decisions).

## Dashboard session

A launch code (`?launch=`) is redeemed once for the `applysmith_session` cookie
and a session key, which travels only in the fragment of the redirect
(`/#k=...`). The page keeps the key in its origin's `localStorage` and sends it
as `X-Applysmith-Session-Key` on every request, the fetch-read board stream
included; a cookie without the key of the same session is `unauthenticated`,
so a cookie another local server on the host received is of no use. A browser
that kept the cookie but lost the page's storage opens a fresh launch link: the
code is redeemed and the same session gets a new key (the old one stops
working); no second session is issued. An unused
launch code is kept until it expires; `POST /api/launch-codes` (admin) mints a
new one, which `applysmith open` and the desktop app's attach use. A page that
gets `unauthenticated` stops and shows the open-from-the-app screen, and
comes back by itself once a new link opened in another tab of the browser
stores its key.

Sessions are kept as SHA-256 digests of the cookie value and the key, in memory
and in `dashboard_sessions` (migration 0045; the last use is written at most
hourly), so a server restart keeps them: 30 days idle, at most 20, the least
recently used evicted, expired rows dropped when the server starts. A backup
restore clears the table.

The CLI side: `applysmith open` (print a fresh link, `--browser` also opens it),
`applysmith pair` (print the bearer token), `applysmith token rotate`. A command that
calls the running server waits up to 30 seconds, saying so once on standard
error, while the server holds the lock but has not written its address or
answers `starting`; a server of another workspace, or one that reports
`degraded`, is refused at once. Every `--json` output of the CLI is the wire
type of the matching route, built by the same exported `api.Wire*` converter:
lowerCamelCase keys, unset times left out, a listing in the route's envelope.

## Decisions

- **The first load after a start.** Once the routes answer, the server
  computes the setup state once in the background (`warmFirstLoad`): it runs
  the one-time machine probes (`sw_vers`, Chrome's `--version`, kept until the
  executable changes) and the keychain presence lookups that the vault then
  keeps, and opens the read connections. Measured on a synthetic workspace
  seeded to a real one's row counts, the setup state's first call fell from
  47 to 78 ms to 2 to 4 ms and every later call from about 30 ms to 4 ms; the
  other reads of Home already answer in 1 to 6 ms. The same warm-up reads
  the day view once; the Gmail password check there uses the vault's kept
  keychain answer (`Vault.Check`), because a keychain tool run on every Home
  load took 30 ms warm and seconds on a busy machine right after a start.
- **Actor from the credential.** A tracker change made through a route is made
  by `user` whether the dashboard session or the local token authenticated it;
  no body carries an actor and an unknown field is `validation_failed`. Block
  entries record the credential kind. The evaluation `source` label defaults
  to `dashboard` or `api`.
- **Runs.** `POST /api/evaluations` and `POST /api/scans` answer `202` with
  `{runId}` and `Location: /api/runs/{id}`. The key is scoped to the
  authenticated principal and the operation; a repeat returns the original run
  (also after a restart), a changed body is `conflict`, and a request that
  joins an active job for the same posting is bound to that job. A scan of a
  source that already has a running record is refused inside the claim
  transaction (`conflict`, no run created), and a repeat of a claimed key is
  never asked again; an in-memory claim of the source covers the moment before
  the scan record exists. The scan run is a `runs` row (`kind` scan); its record is
  the `scan_runs` row named in the final stream event (`scanId`).
- **Streams.** `GET /api/runs/{id}/events` sends `state` (the stored run), then
  `phase` or `progress` events, then `final`, after which it closes. A run that
  ended before the subscriber arrived gets `state` and `final` from the
  database and the stream closes, without a stream being kept for it.
  A scheduled job's progress lines and its end go to the same stream as a
  manual run's (the scheduler reports them), and a scheduled scan carries the
  scheduler's run id in its record's `runId`.
  Cancelling a run publishes a `state` event with status `cancelling` before
  the `202`. Per-run streams are kept 10 minutes after the end. A conversation's stream is
  looked at every 10 minutes and dropped once it has no subscriber and nothing
  was published or opened on it for 10 minutes. Event routes
  answer `GET` only (`HEAD` is `method_not_allowed`). The board topics move as follows: `runs` for run and phase changes,
  `reports` and `tracker` when a report is written, `tracker` for every
  tracker change a route makes, `scans` for scans, the pipeline inbox and
  blocked companies, `answerbank` when `answer-bank.yml` changes on disk,
  whoever wrote it (its time and size are looked at every 2 s), and when a
  suggestion is made, re-proposed, refreshed or reviewed (an apply run's
  events, the scheduled sweep or the page's own request). `configuration` names the workspace file that changed; it also
  moves, naming no file, when a provider entry, a price or an account
  credential is saved or removed and when a provider test ends. A routing, preset or key
  change announces nothing.
- **Reports.** The index row is authoritative; the Markdown and HTML paths it
  names are read only when they are plain files directly under `reports/`. The
  HTML response carries `Content-Security-Policy: sandbox; default-src 'none';
  style-src 'unsafe-inline'; img-src data:`, an explicit type and an inline
  `Content-Disposition`. No route serves a report by path.
- **Apply list.** Placed by `ReadLanes` from the tracker, the list selection's
  evidence (`Selector.Check`), the stored liveness results, report legitimacy,
  the ledger's waiting submissions and linked Gmail receipts; see the Lanes
  paragraph of [apply.md](apply.md). Each item carries the newest run for its
  posting by identity key (`attempt`, outcome only, never a form value), a
  `state` from the closed set (`queued` from the open batch journal or a
  queued start, `running`, then `submitted`, `needs-user`, `failed`, `skipped`
  when only `leftOut` keeps it from running, `idle`), the run id and whether a
  kept tab is open; `counts` carries the items per state and the lane totals.
  An Apply now or Selective item carries `sourceCheck` when its posting's last
  check did not see it live: a stored liveness verdict when there is one
  (`mismatch` is `failed`, `active` says nothing), else its report's
  verification line (`fail` is `failed`; `unverified`, `unknown` or any other
  result than `live` or `pass` is `unknown`); a row with neither has none.
- **The dashboard's reads have a budget of their own** (2026-10-21). A `GET`
  or `HEAD` of a general route by the dashboard session counts against 1,200 a
  minute instead of the general 240; its writes, the local token (extension,
  CLI, MCP) and a paired remote device keep 240. Every page asks for each of
  its cards again when it opens (Home 16 reads, Settings 20), so in a headless
  click-through at 1280 px of fifteen pages with Home between each, one second
  on each page, the 240 were spent within the first half minute: 77 reads came
  back 429 and Home, Usage and Agent control drew "Couldn't load" cards. With
  the read bucket the same click-through sends 321 reads and gets no 429;
  ninety pages in 30 seconds, faster than anyone clicks, send 920. The session
  is accepted on the loopback listener only, with its key and a same-origin
  check, so the bucket guards against nothing but a runaway loop in the page,
  which 1,200 (a page a second, each as heavy as Settings) still stops within
  a minute. A client retry on 429 was left out: at this budget a 429 means
  such a loop, and the card's note already names the wait.
- **Edits carry a version.** `PATCH /api/candidacies/{id}` and the notes route
  require `expectedVersion` of at least 1.
- **Reads do not write.** The story views (`coverage`, `context`, mining
  suggestions) read the knowledge index as the last refresh left it; the server
  reconciles the index with the files at start and every 30 seconds.
- **Errors.** A duplicate candidacy is `conflict` with reason
  `duplicate_candidacy` and `details.matchId`; a document request while a
  run for the same application works is `conflict` with reason
  `document-run-active` and `details.runId`, that run; a stale `expectedVersion` is
  `revision_conflict`; a full evaluation queue is `unavailable` with reason
  `queue-full`, retryable; every route but health answers `unavailable` with
  reason `server-starting` until the database is ready; an invalid `profile.yml` or `portals.yml` is
  `config_invalid` before any run exists. A full disk (SQLite's
  `SQLITE_FULL` or a file write's `ENOSPC`) is `unavailable`, retryable,
  "the disk is full; free some space, then retry", and is still logged; a
  database another process holds locked is `unavailable` "the server is busy;
  retry" after the 5-second busy wait (both checked live 2026-10-17). Start
  writes nothing when the answer bank exists, so a server starts on a full
  disk and serves reads.
- **Keys.** `PUT /api/llm/keys/{provider}` takes `{key}` for a configured
  provider or a preset of an API kind, answers only `keyConfigured`, and its
  body is never logged.
- **Waiting on a model.** A handler answers within 30 seconds unless its route
  sets a `Deadline`. The routes that have a model answer in the request (the
  follow-up and outreach drafts, a Gmail thread draft and summary, a composed
  answer) share `modelDeadline`, 2
  minutes, and the page waits `MODEL_TIMEOUT_MS` (`web/src/api/client.ts`, 130
  seconds; a test holds it above the deadline) through `getModel` and
  `postModel`, so a model that is slow gives its answer, or the thread
  summary's stored-signals fallback, instead of a timeout that cancels the call
  and wastes its tokens. Work with a budget of minutes (story proposals, company
  briefs, the Gmail brief on request) is a background run instead.
