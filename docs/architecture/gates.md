# Apply safety gates

`internal/gates` holds one pure function per gate of the `apply-safety-gates` spec (`openspec/changes/migrate-to-go-mygo/specs/apply-safety-gates/spec.md`). The package is on the pure layer: inputs are plain values, time is Unix milliseconds passed in, and nothing reads a clock, a file, the environment or the network. The caller gathers every fact, calls the gate, and writes the decision as one `gate_decisions` row (`NewAuditRow`; there is no switch that skips it).

A gate returns a `Decision`: `Verdict` (`allow`, `hold`, `deny`), a `Code` from the gate's closed vocabulary (`vocabulary` in `decision.go`), a `Reason` of at most 300 characters that never holds a link, token, key or message text, and a `Class` (`posting`, `environment`, `defect`, `credential`, `answer-gap`) when a deny ends the run. Several gates also return a value (the check or the text to enter). `Decision.Valid` and the suite's `TestMain` enforce that every code of every gate is returned by at least one test.

Identity (posting key, same-candidacy-strict) is computed by `internal/identity`, which gates cannot import; the caller passes the match result as a fact (`LedgerRow.Matched`, `TrackerRow.Relation`). The skip list's word-set comparison is a local copy checked against identity by `TestGates_SkipList_WordSetAgreesWithSameCandidacyStrict`.

## The demo workspace

A workspace whose state directory holds the marker file `.applysmith/demo-workspace` is the demo ([setup.md](setup.md#demo-workspace)). Each gate that guards an outbound action takes a `Demo` input and checks it before any other condition: `SubmitAuthorization`, `AccountCreation`, `ResetStart`, `ActivationLink` and `CaptchaSolve` deny with `demo_workspace`, whatever the request, the setting or the agent says. The actions with no gate of their own go through `DemoWorkspace` (gate `demo_workspace`): Gmail requests and Telegram requests are refused; a document handed to a page is allowed and audited with the page's host, because it is the fictional persona's own (owner decision 2026-10-12: live dry runs upload the demo résumé to real sites and still never press Submit).

The code lookup (`DemoMailCode`, owner decision 2026-10-13) is allowed only when all of these hold: the request comes from an apply run's page walk (`InWalk`), the run does not submit (`DryRun`), the walk stands at a recognised code dialog (`AtCodeDialog`), a Gmail account is connected (`Account`), the persona's address is `local+tag@domain` (`IsPlusAlias`) and its address without the tag is the connected account (`AliasOf`: case-insensitive, and for gmail.com or googlemail.com the dots of the local part are ignored), the address the dialog names, masked or whole, does not contradict the persona's, the sender domain is a known bare domain, the lookup starts no earlier than one second before the dialog opened (`Opened`: the last Send or Resend press, else the first sight of the dialog), and the dialog has taken no code, or one code and its own Resend (`CodesRead`, `Resent`). The reasons name no address. A run that asks to submit is not a dry run, so `--submit` in the demo does not read the code. The persona's address comes from the applicant snapshot (`applysmith demo email` writes it); the connected account from the Gmail state (`gmail.Lookups.Mailbox`, found through the `apply.Mailboxed` interface of the mail lane).

The marker is read where the action happens, never passed down by a caller that might forget it:

| Action | Where the marker is read | What happens |
|---|---|---|
| Final Submit | `apply.Runner.demo` (the run's database, `store.Demo`) in the submit stage | the stage line reads `dry run: demo_workspace: ...`, the run ends `filled`, no claim and no ledger row; its board entry (and the conversation's note) says it stopped before Submit because a demo never submits, not that it waits for the user's Submit (`boardEnd`; live, the agent told the user to confirm a submission the demo cannot make) |
| Account creation, password reset, activation link | the same, in `signup.go`, `reset.go`, `recover.go` | the account stage stops as `credential` |
| Captcha solve | `apply.SolverFactory` from the workspace; the session refuses before its first request | the bot check's reason ends with `demo_workspace: ...` |
| Upload | `apply.docResumes` (the run's documents binding) from the frame origin the engine pins | the page gets the persona's document and an allowed `demo_workspace` decision names its host; an upload whose audit cannot be written is skipped with `upload skipped: demo_workspace` and the rest is filled |
| Upload by the extension | `GET /api/resumes/{id}/file?for=<page origin>` | served, with an allowed `demo_workspace` decision naming the page's host |
| Gmail | the door of every IMAP session (`gmail.Client`, `demoGate`) | a session without one of the two scopes below is refused with `store.DemoRefusal` before it connects |
| Gmail sync, resync, reclassify, digest, alert and sync timers | `Syncer.Run` / `Resync` / `Reclassify`, `Digests.produce` (`Repo.guardDemo`); the digest and alert timers report inactive | the gate's refusal is audited and returned before a run is claimed; the provider is never asked |
| Gmail connection (`mail_connect`) | `gmail.Service.Connect` and `gmail.Service.Test` carry a connect scope in their context | the sign-in, the folder list and an `after:<seconds>` search are served and audited as allowed; the test counts ids and fetches no message |
| Emailed code (`mail_code`) | `apply` code-entry lane (`codeEntryGate`), twice: at the dialog's sight (`noMailWhy`, audited only when refused) and at the lookup (audited either way) | on an allow the lookup's context carries `gmail.DemoCodeGrant(decision, senderDomain, since)`; the session serves only the exact bounded search (`after:<n>` at or after the grant's start, `in:anywhere from:<domain>`, the code vocabulary) and a fetch of the newest 10 UIDs that search answered in each folder, and refuses every other command; a refusal ends the walk as a `verification` stop whose reason carries the gate's |
| Telegram | the Bot API client of the gateway and of `telegram.Manager` | every request fails with `store.DemoRefusal`; the poller does not start |

The apply decisions are audited by the run like every other gate (with its run id); Gmail, Telegram and the résumé route record theirs through `store.GuardDemo`, which writes the row and refuses even when the row cannot be written. Outside a demo workspace `GuardDemo` records nothing.

## Reading text

Every label and message is folded by `foldText` (`fold.go`) before a pattern reads it: compatibility and full-width forms are unified, accents and format characters (zero-width characters, the soft hyphen, direction marks) are dropped, lookalike letters from other alphabets map to Latin, and the result is lowercased. This is what lets one pattern catch "Withdraw", its full-width spelling and the one with a hidden character. The fold depends on `golang.org/x/text/unicode/norm`, already a dependency of the answer-bank matcher, which is also a pure package.

Three rules rest on that fold rather than on a list of bad words:

- The walk presses only a recognised navigation label (`navigationLabels` in `submit.go`), and only when every label the control carries is one. An unfamiliar, destructive or terminal label is denied. The submit stage additionally refuses a label that reads as Submit only through lookalike or hidden characters. In every stage a label with a word spelled from more than one alphabet (`hasMixedScriptWord`) denies the press with `mixed_script_label`: the lookalike map (Cyrillic, Greek, Armenian, Cherokee) is finite, and this fails closed on a lookalike it does not list. "Review application" and "Review your application" are navigation; "Review and submit" is a Submit.
- The computer-use stage (`StageComputerUse`, owner decision F-9) presses only a control of the form the ladder's rung writes. It refuses navigation and a link out of the page (`navigation_in_rung`), a button that submits its form (`submit_in_walk`) and a label that reads as deleting, paying, buying or sending (`destructive_label`, read by the desktop gate's `destructiveLabel`); the rung asks it once with the control's own labels and once with those of the pressable elements at the press point, so a Submit drawn over an option is refused. The walk's choices inside Oracle's history editors (a pill, the editor's Cancel; `oracle.go` `clickChoice`) are pressed under the same stage and audited.
- A checkbox that reads as self-identification (veteran, disability, gender, race or ethnicity, orientation, pronouns, age or birth date) is refused by `ConsentControl` before anything else is read. It uses the vocabulary the ladder excludes by (`selfIDVocabulary`), so the two cannot drift. Such a question is answered only by the answer-bank matcher's self-identification policy (`match/resolve_selfid_policy.go`): the user's own answer or the page's decline option.
- `ConsentInput.Answer` (`AnswerUserBankExact`) is an attestation by the caller: it must have read the user's own bank entry for this exact question. It is never derived from a match score or from a model, and the gate cannot check it. No caller attests it: the gate's four callers (the walk's data-consent page, a policy dialog, the sign-in widget's agreement and the account-details step) pass none, so there an optional box is always left for the user.
- A statement about the application is any "did you ... this application" or "have you applied ..." question plus the named families, so a wording nobody listed still never reaches a model rung. An optional checkbox with no consent wording is left for the user unless the caller attests `AnswerUserBankExact`.
- `LadderFactAllowed` is an allowlist of fact families (`ladderFactFamilies`, plus the explicit `work experience` and `work history` openings) with a veto for identity and demographic words and for any word containing permit, eligib, sponsor, visa, status, authori, citizen or immigra, so a key nobody classified is withheld. A bare `work` opening is not a family.
- `workAuthRE` reads work authorization as a family (a legal, permission or eligibility word near work or employment, either order, plus the sponsorship, visa and immigration vocabulary), not as a list of phrasings.

## Numeric bounds

All are constants in the package, and `TestGates_Matrix_NumericBounds` evaluates each just below, at and just above it: review flag 0.70 and bare phone code 0.85, 3 refused passwords per host, 2 code requests, 2 solves, USD 0.50 floor (`CaptchaBalanceFloorMicroUSD`), 15 minute live window, 24 hour reset hold and credential cooldown, 30 day mail lookup, 120 second solver ceiling and 5 second first solver wait, 300 character reason, 500 skip-list entries of 120 characters, 40 review rows of 120 characters (a longer value is cut to 119 and an ellipsis, and the review is told a value ending so is shown cut short), 160 character audit path, 24 character opaque segment, 8 character token, 20 character hash. The captcha balance also has a ceiling of USD 1,000,000 (`CaptchaBalanceCeilingMicroUSD`), which `TestGates_Captcha_ImplausibleBalanceIsRefusedWithItsOwnReason` evaluates at and above it. The 180 day audit retention (`AuditRetentionDays`) is one rule, `AuditPruneBefore`: the store's prune (`sessions.Store.PruneDecisions`) deletes the rows written before that instant, so a row exactly 180 days old stays. The matrix and `TestGates_Audit_RetentionBoundary` evaluate it just below, at and just above, and `TestDecisions_PruneBoundaryIsARowOlderThanTheRetention` does the same on stored rows. The waits for a mail the run asked for (90 seconds for an activation mail, 120 seconds for a reset mail, polled every 5 seconds) and the 3 second settle after an activation link are constants here too; the account stage's default timing (`apply.AccountTiming`) reads them, and `TestGates_Activation_ResendOncePerRunStrictlyNewerNoGenericResend` pins their values.

## Rules stated here and enforced elsewhere

Some spec rules have no gate of their own, or a gate variant no production code asks, because the product enforces the rule on another path; no decision of theirs is audited:

| Rule | Where the product enforces the rule |
|---|---|
| Self-identification and work authorization come only from the user's own answer or the page's decline option | The answer-bank matcher answers a self-identification or work-authorization question from the user's own entry or the page's decline option (`match/resolve_selfid_policy.go`); `LadderExclusion` keeps every model rung away from it, and `ConsentControl` refuses such a checkbox. |
| Signatures come only from the user's curated name | The matcher's signature route types the user's full-name entry or its initials (`match/resolve_derived_signature.go`) and abstains on a blank name; `LadderExclusion` (`excluded_signature`) keeps every model rung away from a signature. |
| A list resubmit, and the Ask Agent half of `ResubmitDoor` | The Ask Agent's apply tools take no resubmit argument, so only the command line's typed `--resubmit` re-sends, through `ResubmitDoor` (below). |
| List readers hide a failed row | The readers of the ledger leave a failed row out themselves (`ledger/correction.go`, the apply list's `newSelection`); the rule's other reader is the resubmit lane, which the Ask Agent does not have. |
| `ConsentControl` with `Surface: SurfaceSignup`, or with `Answer: AnswerUserBankExact` | A sign-up's agreement is decided by `AccountCreation` (`agreement_needs_setting`); a checkbox of the application form is a question the matcher answers (`match/resolve_option_ack.go`, under the same setting). |
| `CodeRequest` with `CodeMailAlreadyTyped` (`code_already_typed`) | The code lane hands each code mail out once (`codeLane.Lookup`), so the run never holds a code it typed before. |

## Decisions where the text left room

- `ResubmitDoor` is asked by `POST /api/apply/runs` for a request that carries `resubmit`, with the caller the session implies and no list (the route takes one posting): the command line's typed `--resubmit` passes, a dashboard session is refused with `resubmit_caller_refused`, and the decision is audited before a run exists. The Ask Agent's apply tools carry no resubmit argument, so no code reaches the door's Ask Agent wording rules; they state the spec's rule and are held by the gate's own tests.
- The apply run hands every gate the facts it holds, never a constant standing in for one: each audited press carries whether the run is unattended (`Exec.unattended`: the scheduler started it), so `PressControl` refuses every control of such a run with `unattended_caller`; a held host's `PasswordSubmission` is decided from the stored hold facts (`credentials.Hold.Facts`); ADP's Continue and Send passcode are decided on the text the page shows; and the reset gates are asked on every system ([apply.md](apply.md), the reset stage).
- `ResolveSkipList` is asked wherever a batch resolves its rows (`batchSkipEntries` in `internal/api/usage.go`, read by `POST /api/apply/batches` and by the Ask Agent's batch tool): a list of more than 500 entries or with an entry past 120 characters refuses the batch with `unavailable` (503) and the gate's reason, and the refusal is audited with the caller `apply_list`. A key that is no list of strings fails the profile's validation before the gate is asked, so `skip_list_malformed` states the rule for a caller that reads the key raw. The skip-list page reads the list without the gate, so an oversize list can still be opened and shortened.
- Stricter than the spec, deliberately: a Telegram turn is denied both apply tools; `ResubmitDoor` requires resubmit wording as well as the company named in full; the skip list's size bounds stop the batch; an unknown run kind never gets the solver; an unreadable skip list refuses the solver; a held-submit confirmation from Telegram is refused; in a named app the desktop gate presses Space, Backspace and Delete only in a text field the turn's own click or typing put the focus in, since on any other control they press it or remove what is selected.
- Tracker statuses that count as "applied or later" are Applied, Responded, Interview, Offer and Rejected (`AppliedOrLater`); Evaluated, Discarded and SKIP do not.
- The account gate returns `not_user_started` and `system_unsupported` for its prerequisites, and the spec now lists them beside the seven codes of its four checks. Its run input is whether a user started the run, not whether it submits (F-8).
- The advisory model call, the page reads and the ledger writes are not here. A gate only decides from the facts it is handed.

## Legal-declarations setting change

`LegalSettingChange` is not a gate on an action: it is the audit row of the user changing `autoAcceptLegalDeclarations` (gate `legal_declarations_setting`, codes `legal_setting_on` and `legal_setting_off`, verdict allow). `PATCH /api/answer-bank/settings` writes it through `apply.Audit` when the stored value actually changes, with the caller `dashboard` for a dashboard session and `cli` for the local token, so the audit shows when the setting was turned on or off (dashboard-ui, "Turning on legal declarations").
